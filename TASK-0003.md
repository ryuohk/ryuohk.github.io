## Root cause (confirmed by reading the pre-existing diff, not re-derived from scratch)

Two independent gaps let "duplicate-safe" imports still produce repeats:
- `createQuestionId` / content-key computation omitted `correctAnswers`, `mostVotedAnswers`, `explanation`, and `discussion`, so answer variants collapsed onto the same generated ID.
- Import matching trusted supplied capture IDs for pre-existing cards instead of content identity, so re-captures with different IDs (or unrelated sources) created new library entries for identical content.
- There was no consolidation pass over an already-populated library — only new imports were deduplicated.

## What was already done (by a prior session, uncommitted, found in the working tree)

- `packages/core/src/index.js`: `questionContentKey` now serializes exam code, prompt, choices, correct/most-voted answers (sorted sets), vote distribution, explanation, discussion (position-based comment identity, ignoring comment IDs/source URLs), and images (exact data URL or exact src). `createQuestionId` and `makeCaptureBundle` use this for identity and capture-time dedup.
- `apps/web/src/deduplication.ts` (new): `consolidateLibrary` groups cards by `[questionContentKey, cardContentKey]`, picks the earliest-created card as the surviving ID, merges notes/flags/tags, and keeps the most-recently-rated mastery state. `remapIds`/`remapSettings`/`remapSession` translate saved groups, mastery pools, and in-flight sessions from old duplicate IDs to the survivor ID without losing queue/history state. - `apps/web/src/App.tsx`: library/study state is now derived through `consolidateLibrary`, and settings/session state go through the remap functions so the UI only ever shows one entry per equality group. Explicit deletion of a consolidated entry expands to all of its backing cards.

## Bug found and fixed this session

`apps/web/src/App.tsx`: `setStudySettings` and `setStudySession` are plain (non-memoized) wrapper functions that close over `aliases` (the id-remapping map from `consolidateLibrary`, recomputed on every render). `handleRemoteChange` — the cloud-sync callback — is wrapped in `useCallback(fn, [])`, frozen from the first render, intentionally so `useCloudSync` doesn't re-subscribe on every render. Because of that freeze, any state update issued from inside `handleRemoteChange` was permanently using the *first* render's `aliases` (an empty map, since the library starts empty), so alias remapping silently never applied to cloud-driven state merges. Fixed by introducing `aliasesRef` (a ref kept current every render) and having `setStudySettings`/`setStudySession` read `aliasesRef.current` instead of closing over `aliases` directly — this fixes the general class of stale-closure risk (any future memoized callback that calls these setters), not just `handleRemoteChange`, without changing `handleRemoteChange`'s stable identity.
